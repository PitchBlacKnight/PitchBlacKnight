00MIKEL UI — Design System (v7.0)

A design system I build and maintain, published as a Figma library in three editions — Lite, Styles, and Variables — so teams adopt at the level they're ready for. Seven major versions.

  • Three-edition distribution. One component library, three consumption models: no tokens, Figma styles, or full variables. Teams migrate between editions instead of forking the system.
  • Semantic tokens with bound scopes. Purpose-named — bg-brand-primary, border-primary, text-primary — with Figma variable scopes set per property, so a designer choosing a stroke only sees border tokens.
  • Multi-mode theming from a single semantic layer, so components are authored once and re-themed rather than duplicated per theme.
  • Component sets with full variant coverage — buttons (default, destructive, utility, loading, close, groups), input fields, textarea, verification code, modals, and a scoped icon set.
  • Discoverability engineered in. Icon components carry keyword metadata so search resolves by intent — "controller" returns the keyboard icon. The same structured-description layer that makes a system machine-readable.
  • Versioned and governed across seven major releases, with internal-only components marked by naming convention and every update published across all three editions together, so no edition silently falls behind.
01Engineering & Tooling
  • Figma plugins. Built and maintained tooling against the Figma Plugin API to remove designer busywork — most recently a variables-to-W3C-DTCG exporter that lifts a whole token collection out of Figma into a neutral, diffable, versionable format, resolving aliases into DTCG references so the semantic layer survives the export instead of being flattened into duplicates.
  • Web components. Authored reusable, accessible custom elements with full state coverage — every value bound to a token, focus-visible never suppressed, 44px targets, non-colour signals on every state, and aria-invalid / aria-describedby wired into the component rather than left to the consumer. Themed through custom properties, which inherit across the shadow boundary that blocks external stylesheets.
  • Token pipelines. DTCG source → transformation → four platform outputs: CSS custom properties with light and dark modes, resolved JSON, Swift for iOS, and machine-readable system guidance. The build enforces the architecture — it fails on a reference pointing the wrong way up the tier stack and warns on a same-tier one, so governance is a pipeline step rather than a review conversation.
  • Versioning & distribution. Shipped systems as versioned, published libraries with changelog discipline and a deprecation policy — a token leaves the system the way it enters it, marked with a replacement pointer, held one minor version, removed at the next major.
  • Documentation tooling. Storybook and living documentation treated as part of the product — component state coverage, usage and anti-patterns, and accessibility behaviour documented where an engineer actually reads it rather than in a separate wiki.
  • AI-assisted workflows. Authored reusable skill files that encode a system's tokens, component rules, and accessibility standards as machine-readable constraints, so generated output lands on-system and every value is traceable to its source token. Paired with the Figma MCP server and Code Connect to move from design intent to production code without manual translation.
