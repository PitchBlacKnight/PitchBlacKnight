05

The metadata layer

Their bullet: "Identify how the design system, its architecture, and its documentation need to evolve to support reusable skill files and AI-assisted workflows." This is the answer. It's the most specific question in the JD and the one most candidates will handle with a generality.

The two-layer argument — lead with this
Documentation has to split into two machine-readable layers, because they answer different questions. One encodes the rules — tokens, required states, accessibility floors — and it's what makes a generated component correct. The other encodes the inventory — what already exists, when to reach for it, and what never to do with it — and it's what stops the model generating a fourth button alongside your three. Rules without an inventory produce well-formed reinvention. An inventory without rules produces correct selection and sloppy implementation. At your scale the inventory is the more valuable half, because your failure mode isn't malformed components, it's duplicated ones.
  • That last sentence is tailored to them specifically. A company State Farm's size doesn't struggle to build a button correctly — it struggles because eleven teams each built one.
Producer — what a component record holds
component name, category, type, status, since, replacedBy
tokens every visual value bound to a token path
usage useCases, selectionCriteria, commonPatterns, antiPatterns
composition slots, nestedComponents, parentConstraints, forbiddenParents
behavior states — each with its own token overrides and a11y obligation
accessibility role, keyboard, contrast pairs, nonColorSignal, WCAG criteria
provenance source checksum, tokensVersion, reviewedBy
aiHints priority, keywords, context

In keystone-ds/references/metadata.md. Open it if they want detail — the schema is the artifact.

Consumer — how it gets used
  • Read broad, then narrow. System record once per session, layer index per decision, component records only as needed. Reading everything to answer one question is how these get expensive.
  • Select against documented criteria, never aesthetics. The justification quotes the field that decided it.
  • Anti-patterns are hard rules. Never emitted. Overriding one requires an explicit human decision, acknowledged in writing.
  • Verify provenance before trusting a record. Checksum mismatch means stale — prefer the source and report the drift.
  • Flag gaps, don't fill them. A flagged gap is cheap. A shadow component discovered six months later is not.

Shipped as a second skill, keystone-composer. Two skills, because producing and consuming are different jobs with different rules.

The three answers that separate you
  • "How do you stop it rotting?" — the provenance block. Every record carries the checksum of the source it came from and the token version it was generated against. A record whose checksum no longer matches is stale, and the composer refuses to trust it silently. Nothing else I've seen in this space has an answer to this, and it's the question a mature systems team will ask first.
  • "How do you measure it?" — five numbers, from the same pipeline: coverage, stale, unreviewed, untokenised, and thin (records with no anti-patterns, which means nobody has used that component in anger yet). That's their "measuring design system adoption" preferred qual, answered with a report rather than a sentiment.
  • "Isn't this just more documentation to maintain?" — no, and this is the crux: it's generated from the same source as the code. Hand-written guidance rots by definition. The skill file has to fall out of the pipeline, or you've built another wiki page with better formatting.
Know the neighbours before they name them

There is a public, MIT-licensed marketplace of Claude skills doing metadata-driven component composition, and Figma now ships agent skills with its MCP server. Volunteer this. Saying "the pattern is real and converging, here's what the public versions get right and here's where mine goes further" reads as someone tracking their field. Being told about it reads as someone who isn't. Full brief on the landscape page.

Then the strategic frame, which is what a senior hire sounds like: "the plugins worth building here aren't the flashy ones. They're the ones that keep Figma in sync with a source of truth that lives outside it — which is the migration in your JD."

Code "How much code do you actually write?" +

Answer with artifacts, not adjectives. Plugins against the Figma Plugin API, token transformation pipelines, authored web components, and the audit tooling around a system. Plus hand-built sites and interactive tools — this dashboard is one: token layer, keyboard navigation, state persistence, no framework.

Then place yourself honestly, because the framing is a strength rather than a hedge: "I'm not applying as a front-end engineer and you're not hiring one — your JD says hybrid. What I bring is that I can build the tooling and also make the architectural call about what the tooling should enforce. Those are usually two people."

Don't over-hedge. Your instinct is to undersell the engineering half; on this JD that's the half being screened.

Strategy "How would you reduce our dependency on Figma without making designers hate us?" +

This is their hardest question and the one you're best equipped for. Draw the pipeline from section 04, then make the sequencing argument — which is where most people fumble it:

Order matters. "You don't start by taking anything away. You start by making the neutral format the thing that generates Figma, not the thing that replaces it. Designers keep working exactly as they do; the variables in their file just start arriving from the pipeline instead of being hand-maintained. Nothing about their day changes except that drift stops."

Then: "Dependency only becomes a real risk once Figma is the origin. Once it's a consumer, it can stay the best designer experience in the world and that's fine — it just isn't load-bearing anymore."

Close on their own words: "your JD says 'while preserving an excellent designer experience,' and I'd hold you to that. If the designer's day gets worse, the migration failed regardless of how clean the architecture looks."

AI "What makes a design system AI-ready?" +

Three things, and say them as a list — it reads as someone who's thought about it rather than someone improvising.

One — structured, not prose. "Our spacing is based on a 4px scale" in a paragraph is useless. A scale a machine can enumerate is not. Most design system docs fail here immediately.

Two — rules with consequences, not guidance. "Prefer semantic tokens" is advice. "Raw hex is a defect; annotate every value with its source token" is a constraint that produces auditable output.

Three — generated from the same source as the code. A hand-written skill file rots the moment a token changes. It has to fall out of the pipeline, or it becomes another thing nobody updates.

Then the closing line: "Which means AI-readiness isn't an AI project. It's a documentation-quality project with a much less forgiving reader."

Fit "You've been a designer. This role is half engineering." +

Don't apologize for the design half — it's why the role exists. "If you wanted a front-end engineer you'd have written a front-end engineering job description. You wrote one that says 'serve as a Figma expert' and 'explain design concepts to engineering audiences,' which tells me the design half is load-bearing."

Then the substance: "the failure mode of a design-system team staffed only by engineers is a technically excellent system nobody adopts." Adoption is cultural, and that's the part I've spent 19 years on — 350+ contributors at Avant, 40+ product teams on Edison.

And close honest: "I'll be the strongest person in the room on architecture, tokens, accessibility and adoption, and I'll be learning on the plugin and web-component side. If that trade is right for you, it's a good match — and if you need someone who's shipped npm packages for five years, I'd rather you hire them." Willingness to be un-hired for the right reason reads as confidence.

Contract "Rate and logistics" +

$70/hr on a 12-month remote contract with likely extension. Know your own floor before the call rather than deciding live — and know whether that figure is W2 or 1099, because the difference is material and Angela can tell you.

If it's below where you want to be, the leverage isn't "I want more" — it's scope. The JD lists plugin development, web component authoring, token pipeline ownership, and AI workflow architecture. That's a hybrid of two roles, and it's a reasonable thing to name calmly: "the scope here spans design systems architecture and front-end delivery — is there room on rate for the range this covers?"

Ask Angela, not the hiring manager. Recruiters negotiate rate; hiring managers decide fit. Don't mix the two conversations.

Close "Questions for us" — have four +

· "Where do the tokens live today, and what's the current path from a Figma variable to production CSS?" Their answer tells you whether this is a greenfield architecture job or a rescue — and everything you say afterward should adapt to it.

· "When you say reusable skill files, is anyone using them yet, or is this the first attempt?" If it's the first attempt, you're not just qualified, you're ahead of them — and you should say so.

· "What broke that made platform-agnostic a priority now?" There's always a specific incident. Knowing it tells you what success actually means here.

· "How does the design system team sit relative to product teams — central, federated, embedded?" The governance answer tells you how much of this job is politics, which at a company State Farm's size is most of it.

First 90 days

Have this ready unprompted. Contract roles hire on "can you produce value fast," and volunteering a plan answers that before they ask.

01

Weeks 1–3 · Audit and inventory, no changes

Map what exists: where tokens live today, how they reach each platform, what's hand-maintained, where the drift is. Interview designers and engineers about friction — the JD asks for exactly this ("identify workflow friction, adoption barriers"). Produce a countable picture, not opinions.

Precedent the Avant interface inventory — five primary blues, three button shapes, seven sizes. Numbers ended the debate.
02

Weeks 3–6 · One visible automation win

Ship the smallest plugin or script that removes real busywork — a system lint, a variable sync, a token export. Small, fast, and adopted beats architecturally perfect and unused. It also buys the credibility to propose the bigger migration.

Why new contractors get trusted by shipping, not by proposing
03

Weeks 6–10 · Stand up the neutral token source

Tokens into DTCG JSON in Git, with the transformation build behind it. Figma keeps working exactly as it does — it just becomes a consumer. Nothing is taken away from anyone; drift simply stops.

Their bullet "a platform-agnostic source of truth… while preserving an excellent designer experience"
04

Weeks 10–13 · Generate the skill files from that source

Once tokens are structured, the machine-readable guidance falls out of the same pipeline instead of being a separate document. Then prove it: generate a component from the skill file and audit it against the real system.

Their success metric, verbatim "reusable skill files and system guidance that produce consistently aligned outputs"
