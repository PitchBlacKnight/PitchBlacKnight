01

Token & component architecture

Their words: "Maintain and evolve the architecture of our design tokens and web component ecosystem in close partnership with design system engineers."

What they're asking: can you own the architecture, or do you just design inside someone else's?

Primitives stay private, semantics are the public API. That one decision is what lets a system absorb change instead of being replaced by it — at Avant it carried Pathfinder from 2.0 to 3.0 without a redesign. Most recently I owned both layers at Verizon, driving parity across iOS, Android and web, which is where the architecture either holds or doesn't.
Trap Drifting into visual design. They have designers. Stay on layering, naming, and what breaks when you get it wrong.
02

Production-quality web components

Their words: "Build production-quality web components, patterns, and templates aligned with the design system's tokens, standards, and accessibility requirements."

What they're asking: do you ship code other teams depend on, or specs someone else implements?

A component isn't done when it looks right — it's done when every state exists, every value resolves to a token, and the accessibility contract is built in rather than reviewed in. At BCBS that meant React-compatible coded components with theming hooks, handed over without a re-draw. Anatomy is fixed, variants change appearance and never structure, and incomplete state coverage is a defect, not a backlog item.
Trap Talking about components as visual artifacts. Talk anatomy, state coverage, and the contract a consumer relies on.
03

Figma plugins & automation

Their words: "Serve as a Figma expert and develop or maintain plugins that automate designer workflows and improve alignment with the design system."

What they're asking: can you remove busywork, or only document it?

The most recent one exports a file's variable collections to W3C DTCG token JSON — so the tokens can leave Figma and feed a build pipeline. Writing it taught me the interesting problem isn't the API, it's that Figma has one FLOAT type and the token spec distinguishes a dimension from a number. There's no way to know from the API whether 4 means 4px or a 4× multiplier. The real fix is upstream, in the naming convention — which is a design system problem wearing an engineering costume.

Then the strategic frame, which is what a senior hire sounds like: "the plugins worth building here aren't the flashy ones. They're the ones that keep Figma in sync with a source of truth that lives outside it — which is the migration your JD describes."

Trap Listing Figma features. Name one automation, what it replaced, and one thing that surprised you building it. The friction detail is what proves you wrote it.
04

Skill-based system management

Their words: "Advance a modular, skill-based approach to design system management, enabling more workflows and system rules to be automated."

What they're asking: this is the bullet they expect nobody to answer. Show, don't describe. Get the file on screen inside the first fifteen minutes.

I'd rather show you than describe it. This is a skill file — an output contract, reference files for tokens, components and accessibility, and a forced self-check before it returns anything. Two rules make it useful: every generated value carries an inline comment naming the token it came from, so output is auditable rather than trusted; and it has to state its contrast, focus and target-size checks before it hands anything back. Constraints, not vibes.
Trap Describing it well enough that you never open it. The artifact is the answer — talking about it is strictly worse than showing it.
05

Platform-agnostic source of truth

Their words: "Help establish a platform-agnostic source of truth for the design system, reducing its dependency on Figma while preserving an excellent designer experience."

What they're asking: their hardest architectural question. The sequencing is where most people fumble it.

Tokens live in a neutral format in Git — DTCG JSON, diffable, reviewable, versioned — and a transformation build carries them to CSS, iOS, Android, and the docs. Figma becomes a consumer rather than the origin. But the order matters: you don't start by taking anything away. You start by making the neutral source generate the Figma variables instead of replacing them. Designers keep working exactly as they do; the only thing that changes is that drift stops. And I'd hold you to your own clause — if the designer's day gets worse, the migration failed, however clean the architecture looks.
Trap Sounding anti-Figma. The "preserving an excellent designer experience" clause is in their JD because someone already fears this. Say it back to them.
06

How documentation must evolve

Their words: "Identify how the design system, its architecture, and its documentation need to evolve to support reusable skill files and AI-assisted workflows."

What they're asking: the most specific question in the JD, and the one most candidates will answer with a generality.

Documentation has to split into two machine-readable layers, because they answer different questions. One encodes the rules — tokens, required states, accessibility floors — and it's what makes a generated component correct. The other encodes the inventory — what already exists, when to reach for it, what never to do with it — and it's what stops a model generating a fourth button alongside your three. Rules without an inventory produce well-formed reinvention. An inventory without rules produces correct selection and sloppy implementation. At your scale the inventory is the more valuable half, because your failure mode isn't malformed components — it's duplicated ones.
Trap "We'd write better documentation." Name the two layers and name a field. Specificity is the entire answer here.
07

Design intent → production code

Their words: "Improve the connection between design intent and production code so that designers and engineers can move from system-aligned designs to implementation with less manual translation."

What they're asking: your most direct resume hit. Don't rush it.

Two halves. The glamorous one is that the Figma MCP server lets a tool read the actual frame — real variables, real auto-layout, real component names, not a screenshot. The unglamorous one is Code Connect: mapping each Figma component to the real component in the repo so Dev Mode shows an engineer the team's own code rather than a generated approximation. I led that alignment at Verizon across three platforms. The mapping is the half that makes any of it trustworthy, and it's the half people skip.
Trap Making it about speed. It's about trust — generated code nobody believes is worse than no generated code.
08

Finding friction & adoption barriers

Their words: "Partner with product designers and engineers to identify workflow friction, adoption barriers, and opportunities for automation."

What they're asking: do you research your own users, or guess at them?

I shadow people rather than interview them, because nobody describes their own workarounds — they've stopped seeing them. Fifteen minutes watching someone rebuild a quote history from their sent folder told me more than an hour of them explaining their process. Then I make the friction countable: at Avant the interface inventory found five primary blues, three button shapes and seven sizes in production. Numbers end an argument that opinions can't.
Trap "I collaborate closely." Everyone says that. Give the method and the number it produced.
09

Guidance & reusable resources

Their words: "Create clear guidance and reusable resources that help teams use the system consistently and confidently."

What they're asking: can you write for people who aren't you? At their scale this is most of the job.

Documentation is part of the product, not an afterthought. The proof I trust is the Avant marketing library — 350-plus managers and marketers shipping on-brand work with no designer in the loop. That worked because non-designers need harder rails and warmer documentation: the architecture is the same, the empathy is different. And it became the default path because it was faster than the old way, not because anyone was told to use it.
Trap Underselling this as soft. It's the difference between a system that ships and a system that gets used.
10

Governance & technical direction

Their words: "Contribute to the governance and long-term technical direction of the design system."

What they're asking: are you senior? Answer with a concrete failure, not a philosophy.

Governance is mostly deprecation, and almost nobody builds a path for it. I audited my own system's variable collection recently and found three generations of primitive naming coexisting — a lowercase semantic layer, an older PascalCase set, and some bare unnamespaced names from before either. Same values, three conventions, because each generation got added and none got retired. That's not sloppiness, that's what happens without a deprecation path. So governance to me is a contribution route, a version story, and an actual answer to how something leaves the system — not just how it enters.
Trap Abstractions about "stakeholder alignment." The three-naming-generations story is concrete, self-critical, and instantly credible. Use it.
