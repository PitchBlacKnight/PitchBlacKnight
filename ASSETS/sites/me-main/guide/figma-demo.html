What makes it strong

Five things in this library map directly onto their requirements. Know which is which — it turns a portfolio walkthrough into a requirements walkthrough.

Their ask
Three-edition distribution — Lite · Styles · Variables One library, three consumption models. A team on no tokens, a team on Figma styles, and a team fully on variables all pull from the same system and migrate between editions instead of forking it. Answers "token architecture, naming, theming, transformation, and distribution" — the distribution half almost nobody can speak to.
Their ask
Variable scopes bound per property border-primary scoped to STROKE, text-primary to TEXT_FILL, backgrounds to FRAME_FILL and SHAPE_FILL. A designer picking a stroke colour only sees border tokens. "Advanced expertise in Figma — variables, scalable system architecture." This is the detail that proves it rather than claims it.
Their ask
Semantic naming that holds bg-primary · bg-primary_hover · bg-brand-primary · bg-error-primary · bg-success-primary · bg-disabled · border-primary · text-primary. Purpose-based, consistently prefixed, state-aware. Contrast this with the Pathfinder collection — three naming generations and two different navys. Same author, different discipline. That's a governance story, not an inconsistency.

Their ask

Pathfinder — the legacy file

Partner Portal Comps is the older file, superseded by V.3 and MIKEL UI. Keep this section for one reason: the missing-focus-state finding is still the best "what would you improve" material you have.

What's actually true
  • ui/button has Default, Hover, Pressed, Disabled. No Focus.
  • ui/input has State=Focus. So the system knows about focus — the button just doesn't implement it.
  • border/focus = #62A1EB is defined in your variable collection and consumed by nothing on the button. The token exists. The component never picked it up.
Watch this — it just generated a focus-visible ring. I didn't ask for one, and here's the interesting part: the button in my Figma file doesn't have a focus state. The token's defined, border/focus, the input component uses it, the button never picked it up. So the generation just found a real accessibility gap in my own system. That's the argument for encoding rules rather than documenting them — the rule catches what the file forgot.
  • Why this beats a clean run: a perfect match proves the model can copy. A caught gap proves the system has an opinion the file can drift from — which is the entire thesis of the role you're interviewing for.
  • Have ui/input open so you can show the counterpart in five seconds. The contrast is what makes it land as a finding rather than an excuse.
  • Say "in my own system." Auditing your own work in front of them reads as confidence and as someone who runs these tools for real.

04

Variable audit — know this before they run it

From the live collection. The distinction between the three groups is the whole point — get it right and you sound like a systems architect, get it wrong and you sound like a linter.

Correct
Semantic aliasing — leave it alone text/on-primary, bg/card, bg/input, bg/primary all resolve to #FFFFFF. That is the semantic layer working: four different purposes that happen to share a value today and can diverge tomorrow without touching a component. "Eight names for white sounds like a problem until you separate purpose from value. Four of those are semantics doing their job."
Real drift
Three generations of primitive naming, coexisting Same values exposed under three parallel conventions:
· global/white · neutral/grey · brand/primary — current, lowercase/slash
· Color/Neutral/White · Color/Brand/Orange · Color/Neutral/Slate Grey — an older PascalCase generation
· White · Orange · Pink · Background Grey — oldest, no namespace at all "Each generation got added without retiring the last. That's not sloppiness, that's what happens without a deprecation path — which is exactly what governance is for."
Trap
Two different colors both called "navy" brand/navy = #13158C · primary/navy = #191C2F. Not aliases — genuinely different values under near-identical names. This is the one that actually bites someone. Fix this one for real. It's a live footgun, not demo material.
Check
Is the semantic layer aliased, or duplicated? text/primary, bg/button-primary, primary/navy and Color/Brand/Navy all resolve to #191C2F. The MCP returns resolved values, so I can't tell from outside whether the semantics reference the primitives or restate them. If they restate, the semantic layer is cosmetic and a primitive change won't propagate. Open one semantic variable in Figma and check. If it's a raw value rather than an alias, that's the single highest-value fix in the file — and a great thing to have already known.
Tidy
Image credits are in the variable collection Photo by Tyler Nix, Photo by Juan Encalada, Photo by Leon Ell' — image fills living alongside design tokens. Harmless, but it'll show up in any export. Move them to their own collection before you run the exporter in front of anyone.
Verify
brand/primary #FE9800 vs brand/primary-hover #FF9800 One digit apart. Either a deliberate near-imperceptible shift, or a typo that's been in the system a while. Know which before someone asks. Separately: primary button default is navy #191C2F and its hover is orange #FF9800 — a full hue change. Have the reason ready.
The line to have ready
Most of what a naive audit flags here is the semantic layer doing its job — eight names for white is correct, because purpose and value are different things. What's actually wrong is narrower and more interesting: three generations of primitive naming that never got a deprecation path, and two different colors both called navy. That's the difference between a linter and a design systems person — knowing which duplicates are architecture and which are debt.
