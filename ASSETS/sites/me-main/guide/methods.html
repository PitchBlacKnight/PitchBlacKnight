00 — Why this page

Ten moves. Each one has a name, a trigger, and a receipt.

"How do you approach it" is the question people answer worst, because they reach for a philosophy. A method has a trigger — the moment you use it — and an artifact it produces. Naming both is what separates someone who has a practice from someone who has opinions. The green tag on each is the question that triggers it

Pattern-match, don't recite

in the room

You won't get asked "what are your methods." You'll get a situation. Recognise which of the ten it is, name it, then give the receipt.

One receipt each

always

Every method below ends on something that actually happened. A method without a receipt is a preference.

They map to the JD

deliberately

Research, audit, architecture, collaboration, adoption, automation, governance. Their requirement list, in the order you'd actually do it.

01

Discovery & audit

01
"How do you do research?" · "How do you find problems?"

Shadow, don't ask

Watch people do the real work instead of interviewing them about it. Nobody describes their own workarounds — they've stopped seeing them. Fifteen minutes watching someone rebuild a quote history out of their sent folder tells you more than an hour of them explaining their process.

PRODUCES a friction inventory — the specific moments where the tool loses the thread
"I'd rather watch someone work for fifteen minutes than interview them for an hour. Nobody can describe a workaround they've stopped noticing."
02
"How do you make the case?" · "How do you get buy-in?"

Make it countable

You don't win the argument for a system with taste. Inventory every distinct state in production and cluster by pattern — the count ends a debate that opinions can't. Same move applies to a token collection: duplicates, orphans, off-scale values.

PRODUCES an interface inventory · a number nobody can dispute
RECEIPT Avant — five primary blues, three button shapes, seven sizes, in a tool where advisors present live revenue data
"Inconsistency reads as unreliability. But I don't say that until I can show the count."
02

Architecture

03
"Where do you start on a redesign?"

Nouns before screens

Decide what the object is before designing any view of it. Most broken products are organised around tools — destinations you visit and leave — when they should be organised around a single object that carries its own state and evidence.

PRODUCES an object model · a state machine, not a sitemap
RECEIPT Pathfinder — one Project object moving through five states, evidence accumulating forward
"Everything followed from one decision about nouns."
04
"How do you structure tokens?" · "How do you handle theming?"

Primitives private, semantics public

Primitives are the raw scale and nothing may reference them directly. Semantics carry purpose and are the only thing that themes. Component tokens exist where one component must diverge without disturbing everything that shares its semantic — and only there. References point one way, and the build enforces it rather than a reviewer.

PRODUCES three tiers · a build that fails on a violation
RECEIPT Pathfinder carried 2.0 → 3.0 with no redesign · GE Healthcare resolved four theme targets from one semantic layer
"A tier has to earn its keep. Only colour re-themes, so only colour gets a semantic layer — aliasing space-4 as semantic-space-4 adds a hop and no information."
03

Collaboration

05
"How do you work with engineers?"

Name it with the people who call it

Token and component names are an API decision, so engineers are in the room when they're made — before the library gets built, not at handoff. This is the cheapest possible prevention for the design-and-code drift every system eventually gets.

PRODUCES a naming convention with two authors · Code Connect mappings
RECEIPT Verizon — design-to-code alignment through Dev Mode and Code Connect across iOS, Android and web
"They pushed back on my first token names because they read as design words rather than API names. They were right."
06
"How do you support non-designers?"

Harder rails, warmer docs

Non-designers don't need more freedom, they need less — plus documentation written like a person talking. Same architecture as the product system, different empathy. The library has to be the fastest path, not the mandated one.

PRODUCES token-locked templates · enablement sessions
RECEIPT Avant marketing library — 350+ managers shipping on-brand with no designer in the loop
"It became the default path because it was faster than the old way. Nobody was told to use it."
04

Automation & AI

07
"When do you build tooling?"

Automate the third repetition

Not the first — you don't know the shape yet. The third time you hand-fix the same drift is when the tool designs itself, and the tool you build then is the one people actually use. Build the smallest thing that removes the repetition, not the platform.

PRODUCES a plugin · a script · a build step
RECEIPT Figma variables → W3C DTCG exporter, so tokens can leave Figma and feed a pipeline
"Building it taught me the real problem was upstream — Figma has one FLOAT type and the spec distinguishes a dimension from a number. The fix is the naming convention, not the exporter."
WHAT IT BOUGHT roughly 10× on the mechanical work — audits, variant coverage, documentation, drift checks. Zero on the decisions, deliberately.
08
"What's AI's role?" · "How do you make a system AI-ready?"

Encode the rule, don't document it

Prose guidance is unenforceable by anything. A rule with a consequence — "raw hex is a defect", "annotate every value with its source token" — produces output you can audit. Two layers: the rules make a generated component correct, the inventory stops it generating a fourth button alongside your three.

PRODUCES a skill file · component metadata with anti-patterns
RECEIPT A rules pass found a missing focus state in a component I'd owned for three years
"A design system that can't be written down as rules can't be automated by anything. The AI is just the first consumer that can't improvise around bad documentation."
05

Adoption & governance

09
"How do you measure adoption?"

Measure to know what to fix

Coverage is depth — how much of production is built from the system. Usage is breadth — which components get reached for. Detachment tells you where the system doesn't fit, and it isn't automatically bad: on a component built to be customised it may mean it's working. A bare percentage that doesn't point at a next question is theatre.

PRODUCES coverage · detachment · adoption by team · staleness of the docs
RECEIPT Avant — instance audits, changelogs, Dev Mode usage; the qualitative one: design review stopped being about policing basics
"Eighty percent adoption doesn't tell you which teams, or why the other twenty aren't. The number is only useful if it points at the next question."
10
"How do you think about governance?"

Build the exit, not just the entrance

Everyone builds a contribution path. Almost nobody builds a deprecation path — which is why mature systems accumulate generations of names that all still resolve. A token leaves the same way it arrives: marked deprecated with a replacement pointer, kept one minor version, removed at the next major.

PRODUCES a deprecation policy · a versioning story · a changelog people read
RECEIPT Auditing my own file found three generations of naming coexisting — I'd built the entrance and never the exit
"Governance is mostly about how things leave. I only solved how they enter, and I can show you what that cost."
