00 — Why this page exists

You are early. You are not alone.

Both interviews will ask some version of "is anyone actually doing this?" The wrong answer is a shrug. The right answer names two or three real efforts, says what each one gets right, and explains where yours differs — which turns a gotcha into evidence that you track the field. Confidence comes from knowing the neighbours
01

What's out there

Verified by reading the source, not the marketing.

Community skills — the metadata pattern

cris-achiardi/claude-skills — a public, MIT-licensed marketplace of eight Claude skills, five of them design-system focused. The important pair:

  • ai-component-metadata — generates a structured record per component: category, use cases, common patterns, anti-patterns, composition rules, slots, states, an accessibility block, and AI hints.
  • ai-ds-composer — consumes that metadata to select components rather than generate new ones. Reads the hierarchy broad-to-narrow, matches intent against documented selection criteria, treats anti-patterns as hard rules, and flags gaps instead of inventing components.
  • Also there: a Figma variables generator (tokens → Figma, the opposite direction from your exporter) and a codebase indexer that maps component dependency graphs.

Its governing line: "Your suggestions should always map back to documented metadata, not assumptions." That's the right instinct, and it's the same instinct behind your output contract.

Also published as thedesignproject/agent-skills via the skills.sh registry — same schema, same reference files, same generator.

Read the source, not the schema — the gap between them is the story

Installed and read generate_metadata.py. The hand-written Button example in that repo is genuinely good — six states, two real anti-patterns, four composition patterns. The generator produces almost none of it.

  • antiPatterns: [] — always empty. The most valuable field in the schema is a stub the generator never fills. Every anti-pattern in their example was written by a human.
  • Use cases come from a hardcoded name lookup. If the filename contains "button" you get primary-actions, form-submission, navigation-triggers. That's a keyword guess wearing the costume of analysis.
  • Accessibility is asserted, not derived. It writes role: "generic", wcag: "AA" and screenReader: "Properly announced" regardless of what the component actually does.
  • Regex TypeScript parsing. type \\w+Props = \\{([^}]+)\\} breaks on any nested brace, misses interface entirely, and can't see generics.
The schema is the good idea. The generator is a scaffold — and the one part I'd actually push back on is that it writes confident accessibility claims it never checked. In regulated work an unverified "WCAG AA" in a file that looks authoritative is worse than an empty field, because someone downstream believes it. That's exactly why every record I generate is marked unreviewed until a person reads it, and why my accessibility block names contrast pairs a script can verify instead of a grade.

Say that and you've demonstrated three things at once: you read source, you have a regulated-work instinct, and your design decisions are reactions to real failure modes rather than preferences.

Figma's own tooling — first-party
  • The Figma MCP server — one command to connect, then the model reads real frames: layout, variables, component metadata, Code Connect mappings. Both directions; it can write to the canvas too.
  • Figma ships Agent Skills alongside it — for using the plugin API, generating a library from code, and wiring Code Connect. So the "skill file" idea isn't a community experiment any more; the tool vendor ships them.
  • Code Connect — maps a Figma component to the real component in the repo so Dev Mode shows an engineer the team's actual code. You have already done this at Verizon.
The format layer — the boring, durable part
  • W3C Design Tokens (DTCG) format — the neutral, machine-readable token file. It's what makes "platform-agnostic source of truth" a concrete deliverable instead of an aspiration. Already on your resume.
  • Token transformation tooling — the build step that turns that JSON into CSS, iOS, Android, and docs. This is the layer State Farm's JD calls "token transformation or build pipelines."
  • Worth knowing honestly: DTCG has no native concept of modes. Light/dark is still an unsolved question in the spec, and every tool solves it differently. Saying that out loud signals you've actually worked in the format rather than read about it.
02

Where your work actually sits

Honest comparison. Two of these are genuine advantages; one is a genuine gap.

Ahead
Tokens bound into the component record The public metadata schemas describe components — props, variants, states, accessibility — but not which token each visual value resolves to. Yours binds them, and carries per-state token overrides. "Describing a component without naming its tokens documents the shape and loses the system."
Ahead
Provenance — the anti-rot mechanism Source checksum, token version, and a reviewed/unreviewed flag on every record. Nothing public that I read has an answer for what happens when the metadata and the component drift apart — and they always do. "A skill file that isn't generated from the same source as the code is just another document nobody updates."
Ahead
Accessibility as a checkable contract Public schemas carry a flat block — role, keyboard, wcag: "AA". Yours names contrast pairs as token pairs a script can verify, requires a non-color signal, and attaches an obligation to each individual state. Earned at GE Healthcare and BCBS. Say where it came from.
Level
The producer/consumer split They got there first with the two-skill pattern — one generates the inventory, one consumes it. You now have both halves too, but the idea was theirs and it's a good one. Credit it if it comes up. "There's a public marketplace doing metadata-driven composition — the pattern is real and converging" is a stronger thing to say than pretending you invented it.
Behind
Shipped, installed, used by strangers Theirs is public, versioned, installable, and has an audience. Yours is a working artifact used by you. Don't oversell reach. "I built this for my own workflow and it works" is true and sufficient — inflating it is the only version of this that hurts you.
03

What to say, per room

State Farm

Their JD lists skill files and machine-readable guidance under preferred, which means they expect nobody to have them. Position accordingly:

This isn't speculative any more. Figma ships agent skills with their MCP server, there's a public marketplace of design-system skills doing metadata-driven component selection, and the token format layer has been stable for a while. What almost nobody has solved is keeping the guidance in sync with the system — which is why every record I generate carries a checksum and a token version. The interesting problem isn't producing skill files. It's making them not rot.
Goji Labs

They sell AI-accelerated prototyping. Their risk is that it's a marketing line their delivery teams can't cash. Speak to the delivery side:

The tooling has matured faster than most teams have adopted it. The MCP reads real variables, Code Connect maps components to the repo, and the skill layer means output lands on-system instead of generic. What that changes for an agency is the economics — a client can get a real system inside a project budget, which is the thing that always used to get cut.
04

Attribution — the one way this backfires

Rules
  • Demo your own artifact. MIT means you can adapt someone's work; it doesn't make it yours. "I built a skill-based approach" collapses badly if someone in the room recognises a public repo — and this is a small enough niche that they might.
  • Name the neighbours unprompted. Volunteering "there's a public marketplace doing this, here's what it gets right" costs you nothing and reads as someone who tracks their field. Being told about it reads as someone who doesn't.
  • Credit the pattern, own the implementation. The producer/consumer split isn't your idea. The token binding, the provenance block, and the accessibility contract are.
  • Don't inflate usage. "I use this in my own workflow" is true. Anything more invites a question you can't answer.
