02

The demo arc

Same three beats every time, whatever component you run. Nothing here is read verbatim — the "SAY" blocks are the shape of the sentence, not a script.

Beat one — Trust

~30s · before you touch anything

Set the frame first. The room's first silent question is "is this real, or is it a party trick?" — you answer it before the demo starts, not after.

Everything you're about to see is grounded in a skill I built. It holds our tokens, our component rules, our accessibility standards. So Claude isn't guessing — it's working inside our system.
  • Have the skill file visible on screen for two seconds. Don't read it — just let them see it exists.
  • Name the three things it contains: tokens, component rules, accessibility standards. Three is memorable.
  • Say "I built" — this is authorship, not a tool you found.

Beat two — Reveal

~90s · narrate the whole time

Type something deliberately plain. The plainer the prompt, the more impressive the constrained output. Then narrate as it generates — going quiet is the rookie mistake.

Watch — it's reaching for our spacing scale, not inventing its own. And there, it just added a focus state. I didn't ask for that. Accessibility is baked into the skill, so it does it automatically.
  • Narration hook 1 — tokens. Point at a comment: "every value is annotated with the token it came from. That's a rule I wrote, so the output is auditable."
  • Narration hook 2 — unrequested states. "I asked for a button. It gave me six states, because incomplete state coverage is a defect in our system."
  • Narration hook 3 — accessibility. "Focus ring, 44-pixel target, contrast checked in both themes. Nobody asked. It's architecture, not a checklist."
  • Scroll slowly. Point with the cursor. Let them read one thing at a time.
  • Don't read the code out loud. Point at three things and name why they're right.
  • Don't apologize for anything in the output. If something's off, audit it — that's a better beat than a clean run.
  • Don't go silent while it generates. Ever.

Beat three — Meaning

~30s · the close

Zoom all the way out. Answer the two things the room is quietly wondering: is this real, and are you still the designer.

So what used to be a static component in a library is now something the whole team can generate — on-system, on-brand, in seconds. But notice: every judgment call, what's right and what ships, that's still mine. The AI accelerates the craft. It doesn't own it.
  • End on the judgment line. Then stop talking. Let the silence do the work.
  • If they ask a follow-up here, you've won the beat — the demo did its job.

Demo B · Claude Code + Figma MCP

Demo A shows a model working inside a system. This shows the design file and the codebase talking to each other. For an agency selling AI-accelerated prototyping, this is the more valuable half — lead with A because it's faster, but make sure you get here.

Say this first — the one-sentence explanation
MCP is the Model Context Protocol — an open standard that lets a tool like Claude Code talk directly to another application. With Figma's MCP server connected, Claude Code isn't looking at a screenshot of a design. It's reading the actual frame: the real variables, the real auto-layout, the real component names. So the code it writes is bound to your tokens, not to a guess about your tokens.
  • Assume nobody in the room can define MCP. Define it in one breath, then move — don't lecture.
  • The load-bearing phrase is "not a screenshot." That's the entire difference between this and every design-to-code tool they've been pitched before.

Design Systems

Token architecture

Primitives stay private. Semantics are the API. One component, authored once, re-themed everywhere.

space.5 / 24px horizontal padding on the medium button — never 19, never 20
radius.md / 8px every control, one radius token, no exceptions
color.action.bg semantic, not the brand-500 primitive underneath it
focus.ring 2px + 2px offset present in both themes, 3:1 against the surface behind it
duration.fast 120ms one motion token, wrapped by prefers-reduced-motion
error = icon + text never color alone, aria-invalid + aria-describedby wired

Process spine

01

Audit — make the fragmentation countable

Inventory every distinct screen state in production and cluster by pattern. You don't argue for a system, you show the count. Numbers end the debate that opinions can't.

02

Foundations — token architecture first

Primitives stay private, semantics are the public API. Color, space, type, radius, motion. Cross-platform parity is decided here or it isn't decided at all.

Verizon owned primitive + semantic tokens driving iOS / Android / web parity on a mature post-rebrand system
03

Components — full state coverage, accessibility as architecture

Anatomy fixed, variants change appearance not structure. Every state documented — including the unglamorous ones. In regulated work, accessibility isn't a review note, it's the build.

GE Healthcare 100% of components documented with accessibility behavior for regulated review · 4 theme targets from one semantic layer
04

Governance — contribution, versioning, review

A system without a contribution path becomes one person's bottleneck. Naming standards, changelogs, review process, and a clear answer to "how do I add something."

Avant owned Pathfinder end to end, 2.0 → 3.0, two and a half years, no redesign
05

Adoption — enablement, not enforcement

Adoption is cultural before it's technical. Training, warm documentation, one-on-one support, and making the system the fastest path rather than the mandated one.

08

Tough questions

Answers, not scripts. The shape matters more than the words — each one lands on a concrete example.

AI "Isn't this just ChatGPT making a button? What's the design work?" +

The design work is the constraint file. Without it you get a generic button — that's exactly the "everything looks like base input" problem. With it, the model is bounded by our tokens, our anatomy, our required states, our accessibility floor.

Someone had to decide the spacing scale is 4px-based, that there are three button sizes and not seven, that error state is icon-plus-text and never color alone. That's design. The generation is just the part you can see.

Then land it: "I moved the judgment upstream. It used to happen once per component. Now it happens once, in the system, and applies to everything the team generates."

AI "Show me a time AI got it wrong." +
Fill this in by hand — a real one beats any placeholder Structure it in three moves: what it produced → how you caught it → what rule you added so it couldn't happen again. The third move is the whole answer. Anyone can catch a mistake; a systems person turns the catch into a rule.

Candidates from your own work — pick whichever actually happened:

· It invented a token name that looked right but didn't exist in the library, and it read as plausible because the naming convention was consistent. Caught it in review; added the "annotate every value with its source token" rule so unbacked values became visible on sight.

· It produced a component that was visually correct and structurally wrong — right paddings, no focus-visible. Caught in an a11y pass; added the self-check block that forces it to state contrast, focus, and target size before returning code.

· It generated documentation that was confidently inaccurate about a component's behavior. That's the one worth naming out loud — "generated docs are a draft, never a source of truth. Nothing merges without a human review, same as code."

AI "How do you keep AI output from becoming tech debt?" +

Three rules. One — generated code is a draft PR, never a merge. Same review bar as anything a person wrote. Two — the skill is versioned with the system, so when a token changes, the generator changes with it. A stale constraint file is worse than no constraint file. Three — every output is annotated with its source token, which makes drift auditable instead of invisible.

The failure mode isn't bad code. It's plausible code nobody checked.

MCP "What actually is MCP — and why should we care?" +

One breath: "Model Context Protocol — an open standard that lets a tool like Claude Code talk directly to another application. With Figma's MCP server connected, Claude Code reads the actual frame: the real variables, the real auto-layout, the real component names. Not a screenshot."

Then the why, which is the part that matters: every design-to-code tool they've been pitched worked from an image and produced something that looked right and was structurally junk. This works from the data model. The values it writes are the values in the file, because it read them.

Don't lecture. Define it, then immediately show it or move on. The moment you explain a protocol for ninety seconds you've become the person who likes tools more than outcomes.

MCP "Isn't this just fancy copy-paste from Figma? We've seen design-to-code before." +

Concede the history first — it earns you the rest of the answer. "You're right to be skeptical. Every version of this before now produced code no engineer would accept, because it worked from pixels."

Then the three real differences. One — it reads variables, so values are bound rather than transcribed. Two — with Code Connect it knows which components already exist in the repo, so it composes instead of reinventing. Three — it goes both directions, so the Figma file can be regenerated from the code when the code moves ahead. That last one is the difference between a converter and a sync.

And the honest limit, offered before they find it: "It's a strong first draft that a designer reviews. It's not one click, and I wouldn't trust anyone who told you it was."

Agency "How does any of this work when we have twenty clients and short timelines?" +

This is the question the whole interview is really about. Have this cold.

"A real design system has always been something only long engagements could afford. You'd scope it, the client would cut it, and every project would rebuild the basics from scratch. What's changed is the cost. I can stand up token architecture, generate the component set, wire Code Connect, and hand a client something that survives us leaving — inside a normal project budget."

Then make it concrete about them: the constraint at an agency isn't ambition, it's hours. Anything that moves system work from weeks to days doesn't just make design faster — it makes a deliverable sellable that previously wasn't. "That's not a faster mockup. That's a line item you couldn't previously put on a proposal."

Agency "Your background is enterprise and long engagements. We move fast." +

Don't defend the enterprise work — reframe it as the reason you're fast now. "Every hard lesson I have came from systems that had to survive forty product teams and a regulator. I know exactly which parts of that are load-bearing and which parts are ceremony. On a twelve-week engagement I'm not guessing what to skip."

Then the receipt: PBK Studio since 2021 — client work across healthcare, fintech, and insurance, scoped and shipped independently. That's the agency-shaped proof, and it's already on your resume.

And the BCBS line: FIBER was built from zero as a contract engagement. Standing a system up from nothing on someone else's timeline is literally the job they're hiring for.

Adoption "How do you actually measure adoption?" +

Figma has no native analytics, so I triangulate. Audit tooling — Instance Finder and Design Lint to count detached instances and off-system values. Changelog and version tracking across releases. Direct signal — embedded feedback forms, Slack polls, and one-on-ones. Dev-side truth — Git, Dev Mode and Code Connect usage, which is where adoption is real rather than reported.

The qualitative metric I trust most: what brand review meetings are about. At Avant they shifted from policing the basics to arguing about ideas. That's adoption you can feel before you can chart it.

Adoption "What do you do with a team that won't adopt?" +

First I assume they're right. A team that resists is usually telling you the system doesn't cover their case, or the path to using it is slower than the workaround. Both are my bug, not theirs.

Then I make the system the fastest path rather than the mandated one. The Avant marketing library got 350+ people because it was quicker than the old way — not because anyone was told to use it. "A system nobody uses is a wiki page."

Non-designers need harder rails and warmer documentation. Same architecture, different empathy.

Career "You've done a lot of contract work — why?" +

Straight answer: enterprise design systems are staffed that way. GE Healthcare, BCBS, TransUnion, Verizon all brought me in as a specialist to build or scale a system, and in every case the system outlasted the engagement — which is the point of building one properly.

And the counterweight is two and a half years full-time at Avant owning Pathfinder end to end, 2.0 through 3.0, plus the marketing library on the same foundation. That's the long-horizon ownership answer.

Don't be defensive. The pattern reads as repeatedly hired to do the hardest version of this job.

Eng "How do you work with engineering / what about Storybook?" +

I spec with tokens and logic in mind so I'm speaking the same language as the dev team — naming conventions aligned, states enumerated, theming hooks explicit. At BCBS the FIBER components were React-compatible by design, so handoff wasn't a re-draw. At Verizon I led design-to-code alignment through Figma Dev Mode and Code Connect.

On Storybook — be honest and forward-leaning: "I'm actively learning it, because the design-to-dev handoff is the highest-leverage thing in this role and Storybook is where that story ends." Curiosity beats a bluff, and they'll catch a bluff.

I've been building that practice on my own for a while, and it's rare to find a place where it's already the business rather than something you have to justify."

"Second — you work across regulated and high-stakes clients. Root Insurance, k-ID, emergency response. My last seven years have been design systems in exactly those conditions: GE Healthcare's clinical products, Blue Cross Blue Shield's enrollment flows. In that world accessibility isn't a review note, it's whether the product works or doesn't. That's not a skill I'd be learning here."

Then the closing turn — make it about their constraint, not your enthusiasm: "And the thing I actually want to work on is the agency version of this problem. Giving a client a real system inside a project budget, instead of scoping one and watching it get cut. I think that's newly possible and I'd like to be doing it somewhere it matters."

Add one live observation the morning of Open two or three of their case studies and find one concrete thing — a pattern that repeats across their work, a product whose surface you'd ask about. One specific sentence about their work beats three paragraphs about yours. Don't fake it; if you didn't look, skip it.
Fit "How do you tie design decisions to client KPIs?" +

This is verbatim in their job post, so it's coming. The trap is answering with metrics theater — don't recite a dashboard.

The move: tie the design decision to the client's actual cost. Pathfinder is the cleanest example. "The KPI wasn't a design metric. Advisors were losing deals because they couldn't defend a recommendation in the room. So the design goal became: at any moment, can the advisor answer where are we and why this. Everything I designed was measured against that, and the business case for the system underneath it was that inconsistency reads as unreliability when you're presenting live revenue data to a client."

For system work specifically: rework rate, time-to-first-screen on a new project, how much of a build is composed from existing components versus rebuilt. And the qualitative one you actually trust — what brand and design review meetings are about. At Avant they shifted from policing basics to arguing about ideas.

Self "What's your weakness?" +

Pick a real one with a correction attached. The honest version for you: early on I built documentation and governance before the system had earned enough adoption to need it — perfect rails nobody was driving on yet.

The correction: now I ship the smallest usable foundation, get real contributors on it, and let the governance grow out of actual contribution friction instead of anticipated friction. Avant's marketing library was built that way — enablement first, rules second.

Close "Do you have questions for us?" — always have three +

· "When a project ends, what happens to the system you built for that client? Do any of them come back and extend it?" This is the agency-specific version, and it's a genuinely good question — it tells you whether they're building assets or deliverables, and it signals you're thinking past the engagement.

· "Do you carry anything across clients — a starter kit, shared foundations — or does every project start from zero?" If the answer is "every project starts from zero," you have just found the thing you'd fix first, and you should say so.

· "You advertise AI-accelerated prototyping. Where does that actually sit today — is it in the process, or is it a few people using it well?" Shows you read past the homepage, and their answer tells you exactly how much room this role has.

· "What would make you say, a year from now, that hiring for this role worked?" Gives you their success metric in their own words — echo it in the thank-you note.

Loom — required

Goji asks for a ~3-minute Loom as part of the application. Read the brief carefully: how you solved a design problem, with actual work samples. That is a case study, not a tool demo.

Do not get this wrong
  • The instinct is to record the AI demo, because it's the shiniest thing you have. Don't. They asked for a design problem and work samples. Answer the question they asked.
  • Use Pathfinder. It's a real problem, real research, real work on screen, and a real outcome — it's the strongest thing in your portfolio for this brief.
  • Land the AI and systems angle in the last thirty seconds, as the answer to the problem, not as the subject. Then it reads as judgment instead of a party trick.
  • Screen recording with the face bubble on. They're hiring a person.
0:00 – 0:25 · The problem, concretely
I'm Mikel Rosenthal. I want to walk you through one problem. At Avant, technology advisors were running six-figure enterprise deals out of their inbox — requirements in email threads, provider research in spreadsheets, quotes in attachments named final_v3_REAL. Nothing had a state. And the expensive part wasn't doing the work, it was re-finding it.
0:25 – 1:00 · How you found that out
I shadowed advisors through live deals instead of interviewing them about deals — fifteen minutes watching someone reconstruct a quote history from their sent folder tells you more than an hour of them describing their process, because nobody describes their workarounds. They've stopped seeing them. And I ran a full interface inventory: five primary blues, three button shapes, seven sizes, in a tool where advisors present live revenue data to clients. Inconsistency reads as unreliability.
1:00 – 2:00 · The decision, on screen
Everything followed from one decision about nouns. The platform was organized around tools — a fiber tool, a quote tool, each a destination you visited and left. I reorganized it around a single object: the Project. It has a client, a scope, an owner, and a state — and it moves through five of them in order. Evidence gathered in any state stays visible in every state that follows. So at any moment the advisor can answer "where are we" and "why this."
2:00 – 2:35 · The system underneath it
None of that holds without the system. I built Pathfinder underneath it — token architecture, component libraries, governance — and it carried the product from 2.0 to 3.0 without a redesign. Then we extended the same tokens into a marketing library that 350+ people shipped from without a designer in the loop.
2:35 – 3:00 · Where you are now
What I'd add to that today is speed. I build design system rules as skills that Claude works inside, and I use the Figma MCP server so Claude Code reads real variables out of a file rather than guessing at them. It means a client can get a real system inside a normal project budget — which used to be the thing that always got cut. Happy to show that live any time.
  • Have the Pathfinder case study open and scroll it as you talk — the interface inventory diagram and the five-state rail are your two money shots.
  • Three minutes is short. Rehearse once against a timer; if you're at 3:40, cut the research section, not the decision section.
  • One take. Small stumbles read as real; a polished read reads as a script.
